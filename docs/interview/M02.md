# M02 — Bilingual corpus, hybrid retrieval, rerank, eval — Interview notes

## Questions this milestone prepares me for

### 1. RRF or weighted score fusion, and what did your eval show?
RRF (`mineops_retrieval/fusion.py`) sums 1/(k+rank), so BM25's unbounded scores and cosine similarities need no calibration. That robustness is why ADR-0002 made it the default. Measured (`eval/results/retrieval.md`, 63 queries): plain RRF scored nDCG@10 0.827, below dense alone (0.923). Min-max weighted fusion scored 0.892. The cause: BM25 never abstains. Its cross-language fallback always returns 30 candidates, even when they're noise (cross-lingual nDCG 0.069). Rank-only fusion gives that noise equal weight, and it pushed correct dense rank-1 hits down on `x04`/`x05`. Weighted fusion keeps dense's score margin. The cross-encoder on top fixes both (0.954). So RRF stays the default because the agent always reranks.

### 2. Why app-side fusion over OpenSearch and Qdrant instead of one engine's native hybrid?
ADR-0002. One `RetrievalFilter` with two translators (`filters.py`) keeps the engines interchangeable and makes the BM25 / dense / hybrid comparison fair: same filters, same candidate depth, and fusion code I control and can unit test. OpenSearch keeps the mature `english` and `arabic` analyzers; Qdrant keeps filtered HNSW with payload indexes. The cost is two round trips (parallelised in `retriever.py`) and filter logic written twice. I mitigated that with a hypothesis property test (400 examples) and a real-engine test asserting identical chunk-ID sets on 10 filters. Measured p50: BM25 11 ms, dense 141 ms (CPU query embedding), hybrid 161 ms.

### 3. How do you handle Arabic in BM25?
Each chunk's text is indexed three ways (`opensearch_store.py`): `standard`, `english` (stemming), and `arabic`. The `arabic` analyzer removes stop words, normalises alef/hamza/yeh/teh-marbuta variants and diacritics, folds Arabic-Indic digits, and light-stems the ال/و/ب prefixes. Queries route to the analyzer for the detected language (share of Arabic-script letters ≥ 0.3, no dependency), plus a 0.3-boost fallback across all subfields for codes and numbers. Evidence: «الإجراء» and «اجراء» analyse to the same token (integration test); `ar21`, written without hamza, finds the LOTO procedure at rank 1 in every mode. Arabic nDCG is within 0.02 of English for dense and for rerank.

### 4. How did you chunk, and how do you deal with document versions?
The chunker (`chunking.py`) packs whole H2 sections up to 550 BGE-M3 tokens. Oversized sections are split on line boundaries with 60-token overlap, and fragments under 120 tokens merge into a neighbour. Token counts use the embedder's own tokenizer. Result: 65 chunks from 64 docs, median about 450 tokens. Versions are a validity window, not just a flag: `effective_date` plus `superseded_on`, so `as_of=2025-01-01` returns the revision in force then. Without the filter, the best ranker puts a superseded revision first on 4 of 12 trap queries. Near-duplicate revisions can't be separated by relevance, so validity has to be a filter.

### 5. How did you evaluate, and why those metrics?
63 hand-written queries (35 EN, 22 AR, 6 cross-lingual) with 117 graded judgements in `data/eval/`. Grade 2 means the document answers the question in the right revision; grade 1 means related, for example the other-language twin. The metrics (`metrics.py`) are recall@5/10 on grade ≥ 1 (did the candidates include it?), MRR@10 on the highest grade (does the answer come first? that's what the LLM reads), and graded nDCG@10. Results are reported per language group, with p50/p95 latency and a version-filter ablation. Hybrid + rerank: nDCG 0.954, MRR 0.966, cross-lingual nDCG 0.822 vs 0.631 for dense. It's evaluated at document level because 63 of 64 docs are a single chunk.

## Trade-offs to defend

### Cross-encoder rerank vs latency
- Options: no rerank, rerank top 30, rerank a smaller top N, distilled or quantized reranker.
- Chose: `bge-reranker-v2-m3`, 30 → k, as the quality path.
- Why: it's the only stage that fixed cross-lingual errors (+0.19 nDCG) and gave MRR 1.0 on English.
- I'd choose differently when: it's interactive on CPU. About 1 pair/s here makes p50 30.8 s, so go to GPU serving (M9/M11), N=10, or an int8/ONNX reranker, and re-measure the quality loss.

### Real models in tests vs a hashing stand-in
- Options: real BGE-M3 in CI, mocked engines, real engines + `HashingEmbedder`.
- Chose: real OpenSearch/Qdrant (testcontainers) with a deterministic hashing embedder; real models only in `pytest -m models` and the eval.
- Why: CI tests what can break (mappings, analyzers, filters, alias swap) without 4.4 GB of downloads. Semantic quality is measured by the eval, not asserted in unit tests.
- I'd choose differently when: a model upgrade path exists. Then gate on eval regression in CI with cached weights.

### Static `is_latest` vs a validity window
- Options: an `is_latest` flag only, or `effective_date` + `superseded_on`.
- Chose: both. `is_latest` for the common case, the window for `as_of`.
- Why: a flag alone hides the right answer to historical questions ("what was the rule in January 2025?").
- I'd choose differently when: revisions are frequent and long-lived. Then use an explicit `valid_from`/`valid_to` per revision maintained by the document system.

### Fallback multi-match in BM25
- Options: same-language analyzer only, or language-routed plus a low-weight cross-language fallback.
- Chose: the fallback at boost 0.3.
- Why: it catches codes, numbers and acronyms (LOTO-001, WBGT) in the other language.
- I'd choose differently when: fusion without rerank is the serving path. The fallback makes BM25 never abstain, which is what hurt RRF, so I'd drop it or add a score floor there.

## Sovereign / on-prem government deployment
- **Models:** they run fully offline. Mirror the pinned revisions (`BAAI/bge-m3@5617a9f`, `bge-reranker-v2-m3@953dc6f`) into an internal model registry and point `HF_HUB_OFFLINE=1` at it; no Hugging Face calls at runtime. PyTorch CPU wheels come from an internal index mirror (this milestone needed `download.pytorch.org` and `download-r2.pytorch.org`, which an air-gapped site won't have).
- **OpenSearch:** the security plugin must be on (TLS between nodes, document-level security on `site` so the engine enforces site scoping too), with audit logging to the SIEM. Our compose disables it for local use only.
- **Qdrant:** API key + TLS, and the collection per classification level.
- **Rerank hardware:** a GPU node pool or a quantized reranker, because CPU-only rerank (about 31 s/query here) isn't usable for operators.
- **Data residency:** the corpus, embeddings and indexes all stay in-country. Embeddings are derived data and get the same classification as the source documents.
