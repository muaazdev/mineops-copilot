# M01 — Skeleton, compose, schema, synthetic data, CI — Interview notes

## Questions this milestone prepares me for

### 1. How do you apply least privilege to the database behind an LLM agent?
The LLM's data access runs under DB roles that can't do damage even if a tool is misused. Migration `packages/mineops-data/src/mineops_data/migrations/versions/0002_roles_and_grants.py` gives `app_ro` SELECT on `ops.*` only. `drafts_rw` can SELECT assets/sites and SELECT/INSERT/UPDATE `ops.work_order_drafts`, and nothing else. `audit_writer` is a NOLOGIN group role with INSERT only on `audit.tool_calls`, so tools can append to the audit trail but can't read or rewrite it. Both LLM-facing roles get `statement_timeout=5s`. Default privileges cover future `ops` tables for `app_ro`, but deliberately not for `drafts_rw`. `tests/test_roles.py` proves each boundary with `SET ROLE` against a real Postgres (22 role cases).

### 2. How did you design the synthetic data so it has real signal and isn't just random?
Values are caused, not painted on (`mineops_data/generator.py`). Each asset has a failure renewal process, so every failure creates one downtime event plus one linked CM work order. PM work orders are released from `pm_schedules`, and each completed PM adds planned downtime. Daily availability comes from that day's unplanned downtime hours, and ore = target × seasonality × availability × noise. Four anomalies sit on top and are described in `ground_truth.json`. At medium scale, WSP runs at 0.71 attainment against 0.96–1.00 elsewhere. CR-01 logs 19 CMs in 90 days against 5 for the next crusher, JNU has 43 overdue PMs against ≤1 elsewhere, and FRN incidents rise from 1.17 to 3.50 a week after the roster change.

### 3. How do you guarantee reproducibility?
One seeded `numpy.random.Generator` drives everything, UUIDs included (`uuid.UUID(bytes=rng.bytes(16), version=4)`). The window ends on a fixed date (2026-09-30), not "today". CSV formatting is explicit: ISO UTC timestamps, `repr` floats, `\n` line endings. I dropped Faker, so a second RNG stream can't drift. `tests/test_generator.py` pins a golden SHA-256 over every CSV plus `ground_truth.json` for seed 42 / small, and checks that the same seed is byte-identical and a different seed differs. Dependencies are pinned in `uv.lock`, so numpy's RNG output can't change underneath us.

### 4. Why testcontainers instead of mocking or SQLite?
The behaviour under test is Postgres behaviour: CHECK constraints, FK actions, `COPY`, `generate_series`, grants, default privileges, `SET ROLE`. A mock or SQLite can't show that `drafts_rw` is denied on `work_orders`, or that a future table inherits SELECT. `packages/mineops-data/tests/conftest.py` starts one `postgres:16.15` per session, runs the real Alembic scripts, and loads with the real COPY loader. Each test then works in a transaction that's rolled back. The cost is small: container setup is about 3.5 s, and the whole 56-test suite runs in about 7 s locally and in CI.

### 5. Why a uv workspace?
There are three shared packages and two services, with one lockfile (ADR-0001). `pyproject.toml` lists the members, and workspace sources make `mineops-data` import `mineops-core` in place, with no publishing or path hacks. `uv sync --all-packages --locked` in `.github/workflows/ci.yml` fails if anyone edits dependencies without re-locking. Services will build Docker images with `uv sync --package <svc>`, so each image gets only its own dependency closure. It's also fast: CI's install step takes about 1 s with the uv cache.

## Trade-offs to defend

### Text + CHECK constraints vs native Postgres enums
- Options: `CREATE TYPE ... AS ENUM`, lookup tables, or `varchar` + CHECK.
- Chose: `varchar(32)` + named CHECK (`ck_<table>_<vocab>`, see `models.py` `vocab()`).
- Why: adding a value is a constraint swap inside a normal transactional migration. With enums, `ALTER TYPE ... ADD VALUE` has transaction caveats and you can't remove a value. Alembic autogenerate also handles enums poorly (it emitted duplicate CHECKs, which I removed by hand in `0001`).
- I'd choose differently when: a vocabulary needs metadata (labels, ordering, an Arabic name). Then I'd use a lookup table with an FK.

### Grants in Alembic vs grants in the compose init script
- Options: do everything in `docker-entrypoint-initdb.d`, or split it.
- Chose: the init script (`deploy/compose/initdb/01-roles.sh`) only creates LOGIN roles with passwords. Migration `0002` owns all privileges and creates any missing role as NOLOGIN.
- Why: grants are schema policy, so they must be identical in compose, testcontainers and Cloud SQL, and they must be versioned and reviewable. Passwords are platform secrets that don't belong in migrations.
- I'd choose differently when: a platform team manages roles centrally (Terraform / a DB operator). Then the migration only asserts grants exist.

### Denormalised `site_id` vs joining through assets
- Options: derive site from `asset_id`, or store `site_id` on work orders, downtime, incidents and drafts.
- Chose: store it, index it as the leading column, and check it with an integrity test.
- Why: every MCP query starts with the caller's `sites[]` scope (row-level authorisation). The scope predicate should be index-leading and impossible to forget through a missing join. The overdue query runs in about 1.2 ms on medium data.
- I'd choose differently when: assets move between sites. Then a trigger or a generated column would keep them consistent, or I'd join through assets.

### stdlib logging + small formatter vs structlog
- Options: structlog, python-json-logger, or a custom formatter.
- Chose: a stdlib formatter with `contextvars` (`mineops_core/logging.py`).
- Why: it adds no dependency, every library's logs come out as JSON for free, and OpenTelemetry log instrumentation (M8) hooks into stdlib.
- I'd choose differently when: we need rich processor pipelines or bound loggers everywhere. Then structlog in stdlib-integration mode.

## Sovereign / on-prem government deployment
- **Images:** pulled from an internal, scanned registry mirror (Harbor/Artifactory), pinned by digest rather than tag. This milestone already hit Docker Hub 429s; an air-gapped site can't depend on it. The same applies to PyPI: a `uv` index mirror plus the committed `uv.lock`.
- **Postgres:** on-prem HA Postgres (Patroni, or a CloudNativePG operator), or an in-country managed instance. The local superuser `mineops_owner` becomes a non-superuser owner; migrations run from a controlled job. Role passwords come from Vault or an HSM-backed secret store, not `.env`. TLS is required (`sslmode=verify-full`).
- **Audit:** `audit.tool_calls` is append-only by grant. Production adds log shipping to a SIEM and WORM retention, and the auditors' read role is separate from the writers.
- **Data:** even synthetic data stays in-country. Real data would need classification labels on tables and per-site row-level security (RLS) as a second line behind the MCP tool filters.
- **OpenSearch:** the security plugin must be on, with certificates from the government PKI. The `DISABLE_SECURITY_PLUGIN` flag in compose is local-only.

## Numbers worth remembering
- **Medium (seed 42):** 3 sites, 120 assets, 180 PM schedules, 5,512 work orders, 4,824 downtime events, 1,644 production rows (548 days), 278 incidents. Generation takes about 0.9 s, and `make seed` (generate + COPY in one transaction) about 1.8 s.
- **Small:** 18 assets, 274 work orders, 103 incidents, 183 days.
- **Anomalies (medium / small):**
  - A1 attainment: WSP 0.71 / 0.72, others ≥ 0.96 / ≥ 0.92.
  - A2: CR-01 19 / 12 CMs against 5 / 5 for the next crusher.
  - A3 overdue PMs: JNU 43 / 7, others ≤ 1 / 0.
  - A4 incidents per week at FRN: 1.17→3.50 / 1.33→3.25.
- **Tests:** 56 tests in about 7 s (container setup about 3.5 s), 95% line coverage on `mineops_core` + `mineops_data`.
- **Fresh clone:** `make up` 12.7 s, `make migrate` 1.6 s, `make lint` 10.9 s. `make up-all RESTRICTED=1` takes about 100 s, most of it OpenSearch startup. OpenSearch heap is 1 GiB.
- **CI:** about 45 s for the first green run (install about 1 s with cache).
- **Query latency:** about 1.0–1.2 ms for the overdue-by-site query.
