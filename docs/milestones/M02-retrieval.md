# M2 — Bilingual corpus, ingestion, hybrid retrieval, rerank, eval

**Goal:** `make ingest && make eval-retrieval` produces a committed results table comparing BM25 / dense / hybrid / hybrid+rerank, overall and per language.

**Cost:** none (CPU models). Model downloads are a few GB — warn the owner before first download.

**Owner is weaker in OpenSearch — explain mapping/analyzer/query choices in comments and in `docs/interview/M02.md`.**

## Tasks
1. **Corpus generator** (`packages/mineops-data` or a `corpus` module): 60–100 markdown docs with frontmatter per SPEC §5. Template-driven with structured sections (Purpose, Scope, PPE, Steps, Hazards, References). ≥25% Arabic-authored; ~10 topics in both languages; ~8 documents with a superseding newer version. Deterministic. Optional: render ~10 to PDF for PDF-ingestion path.
2. **Chunker**: heading-aware markdown splitter, ~400–600 tokens, overlap ~60, carries `doc_id, section_path, chunk_idx` + all frontmatter; `is_latest` computed.
3. **Filter model**: one Pydantic `RetrievalFilter` (site, asset_type, doc_type, lang, as_of, latest_only) with two translators → OpenSearch bool filter and Qdrant `Filter`. Property-test that both translators agree on a fixture set.
4. **OpenSearch**: index template, `text` field with subfields `text.en` (english analyzer) and `text.ar` (arabic analyzer), plus `title` boosted; keyword fields for filters; `effective_date` as date. Query by detected language; fallback `multi_match` across both. Explain BM25 params (k1, b) and why defaults are kept.
5. **Qdrant**: collection with cosine distance, payload indexes on filter fields, embedder = multilingual BGE-M3-class model (pin exact model + revision). Batch upsert with stable point IDs.
6. **Fusion**: RRF (k configurable) and weighted (min-max normalized) fusion functions, pure and unit-tested.
7. **Reranker**: multilingual cross-encoder (pin), top-N in → top-K out, batched.
8. **`HybridRetriever`** API: `search(query, filter, mode=bm25|dense|hybrid|hybrid_rerank, k)` returning chunks with scores per stage (for explainability and eval).
9. **Eval set** `data/eval/queries.jsonl` (~60 queries: ~35 EN, ~20 AR, ~5 cross-lingual) + `qrels.jsonl` with graded relevance (0–2). Include filter-dependent queries and superseded-version traps.
10. **Eval harness** `eval/retrieval_eval.py`: recall@5/10, MRR@10, nDCG@10, p50/p95 latency, per mode and per language; writes `eval/results/retrieval.md` + JSON.
11. Integration tests with testcontainers OpenSearch + Qdrant on a tiny corpus.

## Notes (implementation, 2026-10-20)

### Decisions agreed at start
- **PyTorch:** CPU-only wheels from the `pytorch-cpu` uv index (`explicit = true`, so only torch comes from it). The lock is limited to Linux x86_64/aarch64 and macOS (`[tool.uv] environments`). Needs `download.pytorch.org` and `download-r2.pytorch.org` on the network allowlist.
- **Test embedder:** integration tests use real OpenSearch 3.9 and Qdrant 1.19 (testcontainers) with a deterministic `HashingEmbedder` and `OverlapReranker`, so CI never downloads model weights. The real BGE-M3 and reranker run in `make eval-retrieval` and in `pytest -m models` (opt-in).
- **Corpus:** generated by `mineops-data corpus` from authored YAML (`mineops_data/corpus/topics_*.yaml`) and committed to `data/corpus/`, since qrels need stable doc IDs and the Arabic text should be reviewable. The optional PDF path is skipped.

### Design notes
- **Corpus:** 40 topics → 64 docs (40 EN, 24 AR = 37.5%), 11 topics in both languages, 13 superseded revisions. doc_id is `<code>-<LANG>-R<rev>`; each superseded revision differs in one concrete fact (e.g. LOTO-001 R1 "up to three workers may share a lock" vs R2 "personal lock each, group lock box above three").
- **Chunking:** H2-aware greedy packing up to 550 BGE-M3 tokens, 60-token line overlap when a section must be split, fragments under 120 tokens merged into a neighbour (soft cap 1.2×). The corpus SOPs are short, so 63 of 64 docs are a single chunk: 65 chunks, median ~450 tokens. Chunk text starts with the document title; `section_path` is kept for citations.
- **Versions as a validity window:** besides `is_latest`, chunks carry `superseded_on`. `latest_only` without `as_of` means `is_latest`; with `as_of` it means "in force on that date" (`effective_date <= as_of < superseded_on`). A static `is_latest` alone would hide the right revision for historical questions. Both translators emit this, and a property test plus a real-engine test check they agree.
- **`site` / `asset_type = all`:** documents scoped `all` match any site or asset filter.
- **OpenSearch:** an index template plus a versioned index (`mineops-chunks-vN`) behind an alias with an atomic swap. `text`/`title` are indexed with three analyzers (`standard`, `english`, `arabic`). The query routes to the detected language's subfields, plus a 0.3-boost multi-match over all subfields that catches codes and numbers in the other language. BM25 k1=1.2 and b=0.75 are kept at their defaults (length-capped chunks, no dev set to tune on). Full reasoning is in the comments in `opensearch_store.py`.
- **Qdrant:** cosine distance, 1024-d, payload indexes (keyword, datetime, bool) on every filter field, point ID = UUIDv5(chunk_id).
- **Language detection:** the share of Arabic-script letters (≥ 0.3), with no dependency.
- **Restricted hosts:** this sandbox reports about 91% disk used, which crosses OpenSearch's percentage watermark and blocks index creation. `docker-compose.restricted.yml` and the testcontainers OpenSearch both use absolute free-space watermarks instead.
- **CPU cost (4 vCPU Xeon 2.1 GHz, no AVX-512):** embedding the 65 chunks with BGE-M3 takes about 89 s. The cross-encoder runs at about 1.0 s per pair at max_length 512, so the default 30-candidate rerank costs about 37 s per query. That's acceptable for an offline eval but not for interactive use on this hardware; see the analysis in `eval/results/retrieval.md`.
